# Publish tagged releases as prebuilt multi-architecture images

Operators install Ohana by running the release's install script or, by hand, by downloading the release's Compose file and pulling prebuilt images; building from source is for contributors only. Every change to `main` runs CI (lint, type check, tests, and the OpenAPI drift check) without publishing anything.

A release happens only when the maintainer pushes a semantic version tag such as `v1.2.0`. The release workflow then runs the CI quality gate, builds the Ohana image for `linux/amd64` and `linux/arm64` on native GitHub-hosted runners, and pushes the platform images to GHCR. Before anything is published under the release version, the workflow pulls the platform images by digest — anonymously, the way operators do — and starts the pinned deployment on both architectures, with Caddy enabled and disabled, and through the release's own install script in its default (no reverse proxy) and external-proxy-network modes, so the operator's one-liners are exercised end to end. Only then does the image receive the version tag. The release is created with generated notes, an Install block on top carrying the exact install one-liners for that release version, and three attached files: the `compose.yaml`, which the workflow pins to the Ohana image of this release, the production environment example (`deploy/env.production.example`), and the install script (`deploy/install.sh`) with the release version and repository baked into it, so the downloaded copy downloads exactly its own release's files and generates the secrets itself — a clean server needs Docker, the Compose plugin, and one command. The installer always installs into `/opt/ohana-core`, wherever it is run from, so every installation's files are found in one known place (`OHANA_INSTALL_DIR` overrides it; CI and the release smoke install into scratch directories that way). Run on a terminal, the installer is a small wizard that asks whether to enable the bundled Caddy (it talks to the terminal itself, so the piped one-liner is asked too); without a terminal, or with `--yes`, it asks nothing. The installer's default serves plain HTTP on a port of the machine, without a reverse proxy; answering yes to the wizard or passing `--caddy-domain` opts into the bundled Caddy serving a domain with automatic HTTPS, and `--external-network` attaches the api to an existing Docker network through a generated `compose.override.yaml` — the pinned Compose file itself is never edited — so a reverse proxy in another Compose project can reach the api. During the smoke the installer's downloads are served locally (the release does not exist yet, which is the point of verifying before publishing), so what is exercised is the script's behavior, not the asset URLs. The attached Compose file names every image explicitly — Ohana at the release version, PostgreSQL, RustFS, and Caddy at tested versions — and never `latest`. The Ohana package on GHCR is public, so operators pull images without credentials. Ohana publishes a single application image: api, worker, and migrate are entrypoints of it, and the built web client is included in it and served by the api process ([ADR-0009](0009-runtime-and-background-work.md)). Everything else in the deployment is an upstream image. Within the repository, `deploy/compose.yaml` reads the Ohana image from the required `OHANA_IMAGE` setting, so building and running from a checkout stays possible.

arm64 is supported from the first release because small home servers such as the Raspberry Pi 5 commonly use it, and native dependencies (image decoding in particular) are cheaper to validate now than to retrofit.
