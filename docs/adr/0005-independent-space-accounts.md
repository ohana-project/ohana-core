# Use independent accounts in each space

Each member belongs to exactly one space. The same person signs in separately to accounts in different spaces; there is no shared identity or account linkage between them. This is the current account model for Ohana.

A device can retain several independent sign-ins and switch between them. This is a client convenience, not a shared server-side identity. Authorization, sessions, personal drafts, gift favorites, and local account data must retain their space/account boundaries; entering one space must not grant access to another.

Only the instance administrator creates spaces. Each space may have multiple owners. Owners may issue access codes only for accounts in their own space; the instance administrator may issue codes for any space, but a code still authorizes only its target member.

The instance administrator uses a separate administrative login and password, with initial setup and emergency recovery available to the server operator. A dedicated administrative area manages spaces, their members, roles, and access-code issuance. The administrator can create a member for themselves and issue its code; using it enters the ordinary member flow, including initial onboarding, rather than turning the administrative identity into a shared identity.

The first instance administrator is provisioned from deployment configuration during first startup. The administrative password is changed through the administrative area after setup; persistent storage keeps its verifier rather than the plaintext password.

Reissuing a code restores entry to the same account and all its existing data, including private drafts and gift favorites. Account data remains attached to the account rather than to a particular code or device. Code issuers are trusted to recover the full account; version 1.0 adds no separate member secret for private data.

An account can stay signed in on several devices at once. A new sign-in adds a session rather than terminating existing sessions. Keep device/session controls minimal for version 1.0, including basic review and revocation, without adding an advanced account-security workflow. The trade-off is separate enrollment and recovery for each space in exchange for straightforward access boundaries.

Issuing a replacement access code invalidates older unused codes but does not terminate active sessions. A separate session-revocation action handles devices that should be disconnected.

Store access-code records in a dedicated PostgreSQL table. Each record identifies its target member and issuer, stores creation and expiry timestamps, and has an explicit issued, redeemed, expired, replaced, or revoked status with the corresponding timestamp. Store only a hash of the code; show the plaintext code once at issuance. A 24-hour unused code can be redeemed once. Reissuing a code preserves the target account and marks prior unused codes as replaced.

Every account in a space is a member with exactly one member role. Version 1.0 has two member roles, owner and regular; a child role is deferred. The instance administrator is not a member role: the administrator creates spaces and provisions members from the administrative area and has no member standing in any space.

Removing a member archives it rather than deleting it. Archiving revokes its sessions and unused access codes and removes it from future reminder recipients; its published entries and attribution remain ([ADR-0007](0007-retain-published-content-and-recover-deleted-entries.md)) and its wishes are hidden but retained. Its private state (drafts and gift favorites) is purged after the trash retention period. An owner or the instance administrator can restore an archived member by issuing a new access code while that private state still exists.

An account's onboarding requires an optional display name and may collect an optional email address or phone number for informational profile display. These contact details are visible to members in the same space but are not login identifiers and are not used for recovery, authentication, or notifications in version 1.0.

Access codes are the only protection against guessing, and version 1.0 deliberately adds no rate limiting: a code is eight characters from a 32-symbol alphabet without ambiguous characters (40 bits), generated by a cryptographically secure random source, valid for at most 24 hours, and usable once. The administrative password is stored with a slow password hash and must meet a minimum length.

On iOS and iPadOS, a Home Screen web app keeps its own cookies separate from Safari, and Web Push works only there. The sign-in flow therefore offers installation first and asks for the access code inside the installed app, so a one-time code is not spent in a browser session the installed app cannot use; continuing in the browser remains available.

After successful code redemption, the API establishes the account session in a Secure, HttpOnly, SameSite cookie. The browser retains the session without exposing the token to application JavaScript.

Each retained sign-in on a device has its own session cookie, named per account. Every request names its intended account explicitly, and the API accepts it only when a valid session cookie for that same account accompanies it; other cookies sent by the browser grant nothing. Sessions stay unlinked on the server, so account switching remains a client-side choice between independent sessions. Offline data on the device is partitioned per account and removed when that account signs out.
